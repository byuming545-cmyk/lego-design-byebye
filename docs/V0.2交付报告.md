# LEGO Speed Creative V0.2 交付说明

Speed Creative 在保留 V0.1 通用创意的基础上，提供受库存与连接规则约束的原创车辆生成、三候选、模块局部修改、锁定、撤销、子装配说明书及 PDF/JSON。Phase 1–9 的代码与演示回归已完成，包括多套合并及用户自报散件页面/API。真实套装与实物验收仍未完成，不能将演示回归当作实际套装证明。

本版工作分支为 `codex/speed-creative-v0.2`，可下载 [分支 ZIP](https://github.com/byuming545-cmyk/lego-design-byebye/archive/refs/heads/codex/speed-creative-v0.2.zip)。Windows 解压启动步骤见 [README](../README.md#windows从-zip-启动)。

## 1. 修改了哪些架构

- 保留 V0.1 的页面、生成器、11 编号目录和验证路径；Speed 使用独立的 `src/speed/` 目录及 `/api/speed` 路由。
- 复用服务端库存 provider、React 页面框架、Three.js 视图、中文字体与 PDF 排版；通过 Speed 适配层绘制参数化汽车零件，不把车辆规则塞入通用生成器。
- 新增 Speed 的零件支持分级、物理单位几何、显式连接点、模块、车辆参数、`candidates[]`、子装配步骤和服务端会话类型。
- 每个候选独立分配同一份库存；服务端保留原始可信库存，编辑请求只发送会话、候选和操作。
- Speed JSON 协商 gzip 压缩，保留完整步骤快照；会话仍为有界内存存储。

源码分工见 [README 项目说明](../README.md#独立模块与-api)。

Speed 目录有 **100 个编号，63 个完整支持、37 个部分支持**，按编号而非套装逐一分类。

| 支持程度 | 当前范围 |
| --- | --- |
| 完整支持 | 50 个基础 Brick/Plate/Tile；7 个 Slope/Curved Slope：`3040b`、`3039`、`11477`、`15068`、`50950`、`54200`、`85984`；SNOT 砖 `87087`、`11211`；现代轮组 `18975`、`3673`、`66727`、`18977`。 |
| 部分支持 | Jumper、其他 Slope/Curved Slope、Wing、Bracket、Modified Brick/Plate、Mudguard、Windscreen、Grille、Round Tile、Seat、其他 Wheel/Tyre/Wheel Holder、Panel 等。可识别，复杂几何或连接尚不完整。 |

支持率按实际件数计算，部分支持和未知零件不计入 `usableQuantity`，尺寸保持 `null`。类型接口里出现一个类别名称，不代表该类别已经完成建模。

## 4. 当前支持多少套 Speed Champions

**在线读取并完成车辆验收的真实 Speed Champions 套装：0 套。实物拼搭验证：0 套。** 尚未完成用户提出的“至少 10 个不同套装”验收。

Rebrickable 适配器可读取任意格式有效的真实套装编号，不再写死两个 Speed 套装；一次最多合并 10 个不同编号。能读取不等于可生成：每盒还必须具备本版本支持的轮架、Pin、轮毂、轮胎和足够结构件。当前也未根据上游主题信息确认输入套装属于 Speed Champions。

本环境没有可用 Rebrickable Key。`DEMO-SPEED` 是独立合成零件池，**不是任何 BMW 或其他官方套装库存**，不计入真实套装支持数量。V0.1 的 `10696/11013` 合成数据仍只供通用流程演示。

真实数据需要服务端 `REBRICKABLE_API_KEY` 及 HTTPS 访问 `rebrickable.com`。Key 不进入浏览器、JSON 或 Git。

## 5. Connection Graph 如何工作

目录声明接口的本地位置、方向、类型、兼容类型及可选配合族。放置后先将坐标转成物理 LDraw 单位（stud 为 20 LDU，plate 为 8 LDU），再按三轴旋转转换世界位置与方向。

只有位置重合、方向相反、类型双向兼容且配合族匹配才建立边。`ConnectionValidator` 从目录独立重建连接图，检查声明边、`activeConnections`、接口复用与全车连通性；实例伪造凸点、Tile 顶部接触、两砖侧面贴靠均不能成为合法连接。`87087` 与旋转 `3005` 的真实侧向接口已用正反例验证。

SNOT 当前只支持已经明确建模的接口，未通用实现所有 Bracket、夹持或铰接结构。

## 6. WheelValidator 如何工作

当前唯一完整轮组族为：

```text
18975 轮架 → 3673 Technic Pin → 66727 轮毂 → 18977 轮胎
```

一辆车需要 2 个轮架、4 个 Pin、4 个轮毂和 4 个轮胎。检查四条实际安装链、可旋转连接、横向轮轴、等高四轮接地、前后轴矩形布局、轮距/轴距、车身离地间隙与轮胎旋转包络。返回 `valid`、`wheelCount`、`groundedWheels`、`collisions`、`rotationalClearance`、`axleConnections` 和警告。

孔轴配合只允许精确就位的已知同轴孔道、狭窄轮胎压配面及 Pin 保留唇标称干涉，不会整对忽略碰撞。轮胎中心孔按空心处理；偏移、缺轮架、错误轮高或轮胎碰侧裙均会失败。几何允许旋转不等于已经实测摩擦、弹性、公差或带载转动。

## 7. StructuralValidator 如何工作

- 底盘自身形成刚性连续网络；承重路径排除自由旋转轴承边。
- 按模块内部每个独立组件分别检查，主结构至少两个相距 1 stud 的锚点；跨度达到 6 stud 时锚点展开至少 2 stud。
- 单条凸点连接不能承担较大结构，避免模块标签或其他牢固部分掩盖弱连接。
- 单点固定只允许 `details` 中最多 2 件、最长不超过 2 stud 的微型装饰；轮组例外只允许有正确轴承链的三件机械总成。
- 模块归属与连接清单必须准确，主要模块不能缺失。

输出模块锚点数与 `structuralScore`。当前通过结构至少 90 分；分数衡量规则符合度，不是重心、扭矩、疲劳、载荷或实物强度结论。库存、碰撞、连接、轮组及结构任一失败都不会输出最终车辆。

## 8. 汽车生成器采用什么模块结构

`VehicleModel` 包含 `chassis`、`front`、`rear`、`cockpit`、`roof`、`leftWheelModule`、`rightWheelModule`、`bodyShell`、`aero`、`details`。每个模块有自己的零件、连接、锁和结构评分，细节模块可以为空。

生成围绕约 8 stud 车宽：先分配关键车顶/尾翼板，实际拼轮架和错缝底盘，再安装四轮、承重车身、驾驶舱、前后外形、车顶、尾翼与饰面。所有选择受实际零件与颜色数量限制。

最多三个方向改变车长、轴距、驾驶舱、引擎盖比例与车顶，不只换颜色。风格与偏好会实际影响支柱高度、4/6/8 stud 尾翼及饰面选择；每个候选独立使用同一库存，不能同时拼三辆。库存或预算不足时允许少于三个，并给真实原因。

## 9. Local Redesign 是否完成

已完成基础版，包括模块锁、候选隔离、失败回滚和 Undo。采用有限中文分句规则，没有调用 LLM。

支持车头降低；尾翼降低、变窄、缩小或放大；车尾更激进；驾驶舱/车顶降低；整车实际降低；模块锁定/解锁。未知分句、额外改色或移动请求整次拒绝，不能只执行识别到的一部分。

目标模块释放库存后局部重建，非目标模块物理数据保持原样，再运行全部 Validator 并重生成步骤。服务器另查原锁、候选 ID 与 `changedModules`。原锁须先单独解锁，不能同次解锁后修改；失败返回原候选。

物理修改保持候选 ID、版本加一；纯锁定不增加结构版本或 Undo。每个候选最多 12 个撤销版本，Undo 保留当前锁状态。会话最多 30 个、1 小时无活动后过期，未持久化，也没有 Redo。

## 10. 哪些仍是 mock 或近似实现

- `DEMO-SPEED` 与 V0.1 的两个演示套装是人工合成库存；真实 provider 已实现，但本环境未做有 Key 的在线验收。
- 自报散件由用户提供数量和颜色，来源明确为“未核验”，不能视作官方库存。
- Three.js 与碰撞使用参数化近似外形，参考固定 LDraw 资料，未打包真实完整 LDraw/CAD 网格。
- 37 个部分支持编号只识别，不使用占位几何生成；未建模功能没有用虚假成功替代。
- 稳定性采用连接规则；自然语言采用有限语法；可容纳 Minifigure 的驾驶舱尚不支持，请求 `minifigure: true` 明确返回 422。

## 11. 当前已知问题

真实套装、实物可拼性和轮胎带载转动尚未验证；一个固定轮组族不能覆盖所有 Speed Champions。轮拱、透明驾驶舱、Bracket 等目录仍需扩展。保守包络可能拒绝现实中可行的紧密排布，有限预算搜索也不保证找到所有可行方案。

说明书已支持四轮独立三件总成、连通且无依赖死锁的尾翼预组装、安装与翻转；未满足预组装条件时逐件装配。指令检查不模拟真实手部操作、压装力或工具可达性。

PDF 为带中文的栅格页面，文字不可搜索，文件可能超过 10 MB。JSON、候选及历史保存完整快照，压缩不降低进程内存占用。三候选完整 JSON 曾从 9,374,288 字节压缩为 332,181 字节，约减少 96%；仍需继续优化快照内存。无永久保存、JSON 导入、账户同步或公网部署。

## 12. 下一轮最需要优化什么

1. 用至少 10 个真实套装库存与实物拼搭核对轮组、连接、装配顺序和结构规则，先补真实证据。
2. 优先扩展经过校准的轮组、Bracket、轮拱、挡风件及人仔空间，而不是扩大未验证的类别计数。
3. 用共享不可变模型与步骤差量降低内存、JSON 和撤销成本，并继续完善库存感知的车型轮廓及局部编辑规则。

## 13. 具体网页测试流程

1. Windows：解压 ZIP，进入可见 `package.json` 的目录，资源管理器地址栏输入 `cmd`；逐行运行 `npm ci`、`npm run build`、`npm start`，每行结束再运行下一行。保持窗口开启，打开 <http://localhost:3001/#/speed>。
2. 默认读取 `DEMO-SPEED`。查看全部库存与三个支持状态；关闭人仔要求，保留默认创意生成。
3. 切换 A/B/C，核对轴距、车长、驾驶舱、车顶和用量改变；每个候选的库存、连接、轮组、结构都应通过。
4. 锁定驾驶舱，提交“车头太高了”。查看版本增加、车头变化，其余模块保留。再提交“驾驶舱降低一点”，应回滚；未知指令或额外改色要求也应整次失败。
5. 切换 B 再回 A，确认互不影响。撤销 A 的结构修改，确认驾驶舱锁仍在；进入通用创意再返回，确认候选、锁、步骤和历史保留。
6. 浏览步骤，找到四轮独立组件、安装页与翻转页。独立拼搭页不应显示整车当作组件；安装页不重复取件，翻转页新增 0 件，最后主车包含所有模型零件。
7. 导出 PDF 与 JSON。已测 74 件例为 39 步（20 build / 10 subassembly / 5 attach / 4 rotate），PDF 41 页、11.12 MB、Chromium 约 4–6 秒；其他输入不要求相同页数。
8. 有 Key 时才测试真实编号，例如 `76922 + 76924`；这些编号目前只是格式示例。没有 Key 必须显示错误，不能用 DEMO 冒充真实库存。重复编号不增加盒数。
9. 展开“添加自有散件”，添加 `3034`、黑色、2 件，再添加未知编号 `unknown-speed-part`、1 件。点击“读取库存”后，检查按色合并与 `CUSTOM-EXTRAS` 用户自报来源；未知件应显示未支持，不参与生成。重新生成应仍通过全部校验。删除散件行并重新读取，应恢复原库存数量与来源；未点击“添加散件”的输入不计入库存。
10. 返回 V0.1，生成 `10696` 机器人，检查 3D、分步与 PDF。不要在 Speed 中将 V0.1 静态积木汽车当作可转动车辆。

开发验证命令：`npm test`、`npm run build`、`npm run test:e2e`、`npm run test:preview`。浏览器测试需 Chromium，见 [README](../README.md#验证命令)。最终结果：
